# 洞察引擎：会话内的超然旁观者

> 本文档是 `chain-design-final.md` 的扩展规格，定位为**洞察模块的教学表述与设计背书**。
>
> - `chain-design-final.md`：终局规格文档，定义五链图鉴的整体骨架与提取协议
> - `融合进阶.md`：链间化学反应的催化酶设计（模型侧 CoT 推演指导）
> - `洞察引擎.md`（本文档）：系统侧的超然层——从链图全局状态中提取认知趋势，产出建议而非指令
>
> 三者关系：图鉴（`prompt.ts`）让模型**内化**认知结构；快照（`snapshot.ts`）让系统**记录**链演化；洞察引擎（`insight.ts`）让系统**理解**链演化的全局含义。模型负责"想"，快照负责"记"，洞察负责"看"。

---

## 零、为什么需要洞察引擎

### 问题：系统有数据，但没有理解

当前系统的数据流是：

```
模型回复末尾 JSON 快照
      ↓
parseSnapshot()        解析 JSON 行
      ↓
mergeSnapshotIntoGraph 融合入 ChainGraph（单链内演化记录）
      ↓
buildGuide()           元数据投射（GPS/轨道图/缺口）
      ↓
  到此为止
```

ChainGraph 忠实记录了每条链"发生了什么"——哪个角色填充了、哪个修正了、哪个作废了。ChainGuide 把它投射成人类可扫读的 GPS 坐标和轨道图。

但这两层都有一个结构性盲区：**只看单链，不看全局。**

`guide.ts` 逐链扫描 `[causal@1]`、`[logic@1]`...，每条链独立报告进度和缺口。它不会告诉你"因果链的归因和时间链的过去正在重叠"——因为那需要同时看两条链的内容。它也不会告诉你"因果链的置信度已经连续 3 轮下降"——因为那需要跨轮次追踪历史趋势。

### 洞察引擎补的正是这个缺口

它站在系统之上，以全局视角审视整个 ChainGraph，从五个维度提取认知趋势信号：

| 维度 | 看什么 | 发现什么 |
|------|--------|----------|
| 链间化学反应 | 多链 nodes 的内容交叉 | 两条链的对应角色内容重叠 → 化学反应苗头 |
| 链迁移预测 | 主链进度 + 其他链状态 | 主链即将收束、用户可能切换关注点 |
| 置信度趋势 | 跨轮次 confidence 变化 | 置信度连续下降 → supersede 风险 |
| 脉络缺口聚合 | 多链 gaps 交叉分析 | 多条链同时缺终结角色 → 认知盲区 |
| 分歧收敛预测 | diverged 节点状态 | AI 与用户分歧悬而未决 → 需要收敛 |

### 关键定位：超然层

洞察引擎是**观察者，不是参与者**。它的产出是"建议"，不是"指令"：

- **不修改 ChainGraph**——只读，不写
- **不注入 system prompt**——不占用模型的 token 预算
- **不进入 prestep**——不干预 CoT 的推理过程
- **不影响快照协议**——不改变模型的打标行为

它只做两件事：
1. **对模型**：通过 `get_insights` tool 暴露洞察，模型**按需调取**，参考性质，可以采纳也可以忽略
2. **对用户**：维护推荐话题候选池，按需渲染（会话结束便条 / 未来 UI 按钮）

这跟 prestep 的强制注入有本质区别——prestep 是"手上的指挥棒"，洞察是"桌面上的参考卡片"。模型选择调取 `get_insights` 这个动作本身，是 CoT 自主决策的一部分，而不是被外部注入影响。

## 一、五大分析器详解

### 分析器 ①：链间化学反应检测（CrossReactionAnalyzer）

**检测什么**：两条链的对应角色内容是否发生重叠——如果是，说明 CoT 正在自发产生链间嫁接。

**设计依据**：`融合进阶.md` 定义了四大经典链间化学反应。每种反应都有特定的链配对和角色配对：

| 反应 | 链 A | 角色 A | 链 B | 角色 B | 反应名称 |
|------|-------|--------|-------|--------|----------|
| 1 | 因果链 | 原因 | 时间链 | 过去 | 深层归因动力学 |
| 2 | 逻辑链 | 前提 | 操作链 | 步骤 | 抗脆弱执行手册 |
| 3 | 叙事链 | 转折 | 因果链 | 原因 | 沉浸式深度诊断 |
| 4 | 时间链 | 未来 | 叙事链 | 结局 | 变革蓝图 |

**检测算法**：

1. 扫描 ChainGraph，取每种链的最新活跃根链
2. 对每个反应配对，取两条链对应角色的节点内容
3. 用关键词交集检测内容重叠：提取两段文本的关键词（长度 >= 2 的分词 token），计算交集数量
4. 交集 >= 2（`OVERLAP_THRESHOLD`）→ 报告"XX 苗头"

**为什么用关键词交集而不是语义相似度**：

初版设计刻意不引入 embedding。原因有二：
- **轻量优先**：洞察引擎是每轮执行的附加处理，不应引入额外的模型调用开销
- **精度够用**：化学反应检测只需要"有没有重叠"这个布尔信号，不需要精确的语义距离。关键词交集 >= 2 已经足以过滤掉偶然的词汇碰撞
- **未来升级路径**：如果初版跑下来发现关键词交集误报率高，可以平滑升级为 embedding 相似度，只需替换 `keywordOverlap()` 函数

**产出示例**：

```
type: cross-reaction
severity: info
title: 深层归因动力学苗头
detail: 因果链的原因与时间链的过去内容重叠（3个共同关键词）。
        单用因果链只能找到"当下的直接原因"，叠加时间链能看清"根因是怎么一步步长成今天这样的"。
```

**设计哲学**：洞察引擎不判断化学反应"好不好"——它只报告"正在发生"。是否展开嫁接完全由 CoT 自己决定。这符合超然层定位：提供信息，不提供判断。

---

### 分析器 ②：链迁移预测（MigrationPredictor）

**检测什么**：主链的推进状态是否暗示用户即将切换认知焦点。

**两种迁移信号**：

**信号一：主链即将收束**

当主链进度 >= 2/3 且缺口在末尾角色时，意味着这条链即将走完。例如因果链已填充"问题"和"原因"，只差"方案"——收束后用户很可能转向新的认知方向。

```
type: migration
severity: info
title: 因果链即将收束
detail: 主链进度 2/3，末尾角色解决方案仍缺。收束后可能转向其他链。
```

**信号二：其他链已有节点**

当主链推进中（进度 >= 1/3），同时其他链也已有活跃节点时，说明用户的认知地图不只在一条链上。用户可能在多个维度同时思考，迁移随时可能发生。

```
type: migration
severity: info
title: 链迁移可能
detail: 主链因果链推进中，同时逻辑链、时间链已有节点。用户可能即将切换关注点。
```

**为什么是 info 而不是 warn**：链迁移是正常的认知流动，不是异常。洞察引擎只是提示"可能发生"，让模型在调取 `get_insights` 时有全局视野。模型完全可以选择忽略——如果它判断当前链还有深度可挖。

---

### 分析器 ③：置信度趋势预警（ConfidenceTracker）

**检测什么**：同一节点跨轮次的 confidence 变化趋势。

**工作原理**：

1. 每轮分析前，先调用 `updateConfidenceHistory()`：扫描所有活跃节点的 confidence 值，追加到 `InsightStore.confidenceHistory`
2. `confidenceHistory` 的 key 是 `${kind}@${root}:${role}`（如 `causal@1:cause`），value 是历次 confidence 值的数组（最新在末尾，最多保留 10 条）
3. 然后扫描所有有 >= 2 条历史的 key，计算连续下降次数

**三档预警**：

| 条件 | 严重程度 | 含义 |
|------|----------|------|
| 连续下降 >= 3 轮 | critical | supersede 风险极高——这个结论可能已经站不住脚了 |
| 连续下降 >= 2 轮 且最新 < 0.4 | critical | 置信度已跌入危险区——结论很可能被推翻 |
| 连续下降 >= 2 轮 | warn | 趋势需关注——结论的可靠性正在下降 |
| 连续下降 < 2 轮 | 不报告 | 正常波动 |

**为什么追踪到角色粒度**：

同一根链上不同角色的置信度可能独立变化。因果链的"问题"置信度可能一直很高（因为问题描述是事实），但"原因"的置信度可能连续下降（因为归因推断被新证据动摇）。角色粒度的追踪能精确定位"哪个环节在动摇"。

**与 supersede 的关系**：

`supersede` 是模型主动声明"废旧旧链"的机制。但模型不一定每次都会及时 supersede——有时新证据是渐进积累的，模型可能迟疑。置信度趋势预警就是系统侧的"早期雷达"：在模型还没下定决心 supersede 之前，先提示"这个结论在动摇了"。

**但洞察引擎不会替模型做决定**——它只报告趋势。是否 supersede 仍然完全由模型在下一轮回复中自主判断。这是超然层原则的体现。

---

### 分析器 ④：脉络缺口聚合（GapAggregator）

**检测什么**：多条链是否同时缺少终结角色——如果是，说明用户在多个维度寻求结论但尚未收敛。

**终结角色**：

每条链的最后一个角色是"终结角色"——它代表该链的认知闭环：

| 链类型 | 终结角色 | 闭环含义 |
|--------|----------|----------|
| 因果链 | 方案 | 找到解决方案 |
| 逻辑链 | 结论 | 得出推论 |
| 操作链 | 结果 | 确认产出 |
| 叙事链 | 结局 | 故事落幕 |
| 时间链 | 未来 | 看清方向 |

**检测规则**：

扫描所有活跃链的 `gaps`，统计终结角色的缺口数量。>= 2 条链同时缺终结角色 → 报告"认知盲区"。

**产出示例**：

```
type: gap-aggregation
severity: warn
title: 多链终结角色缺口
detail: 因果链的解决方案、时间链的未来均未填充。
        用户可能在多个维度寻求结论但尚未收敛，认知盲区较大。
```

**为什么有价值的**：

单链缺口在 `guide.ts` 的 GPS 坐标里已经可见（`进度:问题✓→原因✓→方案✗`）。但跨链的缺口聚合是单链看不到的——它揭示的是一种"结构性的未完成"：用户开了多条认知线但都没走完。这可能意味着：
- 用户在探索阶段，还没准备好收敛
- 用户被多个问题困扰，不知道先解决哪个
- 对话偏离了主线，各条链都被搁置了

洞察引擎不做这些细分判断——它只报告"多条链同时缺终结角色"这个事实。模型拿到这个信息后，可以自己决定如何回应（比如建议用户先聚焦一条链）。

---

### 分析器 ⑤：分歧收敛预测（DivergenceWatcher）

**检测什么**：AI 与用户的路径分歧是否已经收敛，或者持续悬而未决。

**背景**：

快照协议支持 `diverged` 形态——当 AI 和用户对同一角色有不同的推论时，并行记录两条路径：

```json
"原因": {"ai": "人力不足", "user": "需求混乱"}
```

也支持 `converged` 形态——双路径在下游重叠时，声明合流继承：

```json
"方案": {"value": "优先级裁剪", "from": ["ai", "user"]}
```

**检测规则**：

1. 扫描所有活跃节点中的 diverged 节点（`node.divergence === 'ai' | 'user'`）
2. 按 `${rootKey}:${role}` 分组，找到同一角色下的 ai 路径和 user 路径
3. 检查该 rootKey+role 下是否存在 converged 节点（`node.convergedFrom` 非空）
4. 如果存在 converged → 报告"分歧已收敛"（info）
5. 如果 ai 和 user 都存在但没有 converged → 报告"分歧悬而未决"（warn）

**产出示例（悬而未决）**：

```
type: divergence-watch
severity: warn
title: causal@1的原因分歧悬而未决
detail: AI 推论"人力不足"与用户路径"需求混乱"分歧尚未收敛。
        建议在后续轮次中寻求合流或确认哪条路径成立。
```

**产出示例（已收敛）**：

```
type: divergence-watch
severity: info
title: causal@1的原因分歧已收敛
detail: AI 与用户在原因上的分歧已通过合流解决。
```

**为什么重要**：

分歧悬而未决是对话中的"隐性债务"。模型和用户各执一词，如果不显式收敛，后续的推理会建立在哪条路径上？如果是错误的路径，整个链的结论都会有偏差。

但洞察引擎不会"催促"模型去收敛——它只报告"这里有分歧，还没解决"。模型可能在下一轮自然地引导用户确认哪条路径成立，也可能判断这个分歧不重要可以忽略。决策权在模型。

## 二、推荐话题生成器

### 设计理念：推荐，不是追问

推荐话题生成器是洞察引擎对用户侧的核心产出。它的定位非常明确：

> **基于全局洞察后的高维推荐，不是追问。**

追问是"你还没说XX"——那是补缺，是链内视角，是任何聊天机器人都能做的事。

推荐是"我看懂了全局之后，发现你可以往这个方向想"——那是升维，是超然视角，只有真正理解了对话脉络的系统才能做到。

两者的区别：

| 维度 | 追问 | 推荐 |
|------|------|------|
| 视角 | 链内（看到缺口） | 全局（看到洞察） |
| 意图 | 补全信息 | 打开新认知方向 |
| 语气 | "你还没说XX，说说看" | "我注意到一件事，也许值得想想" |
| 用户感受 | 被催着补作业 | 被引领着看到新风景 |
| 数据来源 | 链图缺口（guide.gaps） | 洞察结果（InsightItem[]）+ 链图内容 |

### 话题必须带着上下文

好的推荐话题不是干瘪的通用问句，而是带着具体对话内容的"有锚点"的推荐。话题生成器会从链图中提取已填充角色的内容，嵌入到话题中，让用户感受到"AI 真的读懂了我们的对话，而不是在套模板"。

例如，不是"把两个问题联系起来看会怎样？"，而是"刚才聊到'需求失控'，但我注意到这件事可能不是孤立的现象——如果把时间线拉长来看，它会不会是一个更大趋势的一部分？"

### 两种话题形态

**延展型（extension）**：洞察发现了值得深挖的新方向

生成规则（每条都从具体的洞察结果中提炼）：

1. **化学反应苗头** → "我注意到这件事可能不是孤立的——它会不会是更大趋势的一部分？"
   - 不是"这两条链有没有联系"，而是"我看到了联系，它意味着什么"
   - 锚点：主链第一个已填充角色的内容

2. **置信度下降** → "我现在的判断可能不够全面——有没有遗漏的角度？"
   - 不是"置信度降了"，而是"我对这个结论开始不那么确定了"
   - 锚点：该链的起始角色内容（problem/beginning/past 等）

3. **分歧悬而未决** → "与其二选一，不如想想背后是不是藏着同一个更深层的原因？"
   - 不是"哪个对"，而是"两种看法背后有没有更深的共同原因？"
   - 意图：超越分歧，而不是消除分歧

4. **多链终结角色缺口** → "你在多个方向同时探索，如果先聚焦一个突破，其他的会不会更容易解决？"
   - 不是"你有好几个问题没解决"，而是"也许先突破一个点会带动全局"
   - 锚点：主链第一个已填充角色的内容

**收束型（convergence）**：全局状态表明该进入下一阶段了

生成规则：

5. **主链完整且置信度稳定** → "这个方向站得住，不如先小范围试一下看看反馈？"
   - 不是"分析完了"，而是"思路已经清晰，现在最有价值的事情是验证它"
   - 锚点：主链终结角色内容（方案/结论/结果等）

6. **链已收束且有其他链活跃** → "刚才理清的结论，能不能用来重新审视另一个问题？"
   - 不是"接下来做什么"，而是"一个领域的答案正好是另一个领域的钥匙"
   - 锚点：已收束链的起始角色内容 + 活跃链的起始角色内容

7. **链已收束且无其他活跃链** → "有没有其他一直在困扰你的事？换个角度说不定比从零开始容易。"
   - 不是"还需要什么帮助"，而是"换一个被困扰的问题，用清了的大脑去看"

### 话题不自动展示

推荐话题候选池每轮更新，但**不自动展示给用户**。原因：

- 每轮底部自动推送话题会打断对话流
- 用户可能在深度思考中，不想被"你可以问这个"分心
- 自动推送会让洞察引擎从"超然层"变成"干扰层"

当前版本的话题写入日志，供未来 UI 集成（如 `/insights` 命令或会话结束便条）。

### 话题上限

保留最近 10 条（`MAX_TOPICS = 10`）。多了信息过载，少了可能漏掉有价值的。话题去重：同 question 已存在则跳过。

## 三、生命周期与会话绑定

### 核心原则：随会话生灭

洞察引擎的存储（`InsightStore`）跟 ChainGraph 一样，是会话内临时数据。会话删除 = 链图 + 洞察 + 置信度历史全部清空，无残留。

跨会话的趋势分析是 `agent-memory` 的职责，不是洞察引擎的活。洞察引擎只负责"当前会话内的认知趋势"——这保证了它轻量、无状态污染。

### 销毁流程

```
session/disposed 事件触发
  ↓
hook.ts 的监听器执行：
  1. index.dispose(sessionId)      ← 清空 ChainGraph
  2. insightEngine.dispose(sessionId)  ← 清空 InsightStore（洞察 + 话题 + 置信度历史）
```

两个 dispose 在同一个 `session/disposed` 监听器内顺序调用，保证原子性——不会出现链图清了但洞察还在的半销毁状态。

### 存储上限

| 存储项 | 上限 | 淘汰策略 |
|--------|------|----------|
| 洞察项（insights） | 20 条 | FIFO（先进先出） |
| 推荐话题（topics） | 10 条 | FIFO + 去重 |
| 置信度历史（confidenceHistory） | 每 key 10 条 | FIFO（最早的被挤掉） |

洞察项有去重机制：同 type+title 已存在则更新（刷新时间戳和内容），而不是追加新条目。这避免了同一信号在多轮中被重复报告导致列表膨胀。

## 四、模型侧接口：get_insights 工具

### 工具定义

```
名称：get_insights
描述：获取当前会话的认知洞察建议（链间化学反应/迁移预测/置信度趋势/缺口聚合/分歧收敛）。
     参考性质，非约束——你可以采纳也可以忽略。需要全局视角时调用。
参数：
  type（可选）：筛选洞察类型
    - cross-reaction：链间化学反应检测
    - migration：链迁移预测
    - confidence-trend：置信度趋势预警
    - gap-aggregation：脉络缺口聚合
    - divergence-watch：分歧收敛预测
    不传则返回全部
返回：
  insights: InsightItem[]    ← 洞察建议列表
  topics: RecommendationTopic[]  ← 推荐话题列表
```

### 为什么做成 tool 而不是 system prompt

1. **token 效率**：图鉴 prompt 是静态的、稳定的认知框架注入；洞察是动态的、每轮变化的。如果把动态内容塞进 system prompt，每轮 token 开销都在变，且模型需要反复重新解析

2. **语义天然匹配**：tool 的语义就是"按需调取"——模型觉得需要全局视角时自己调，不需要时不占 token。这完全符合"桌面上的参考卡片"定位

3. **超然层纯粹性**：tool 调用是模型主动行为，意味着模型"选择参考建议"这个动作本身是 CoT 自主决策的一部分，而不是被外部注入影响。如果做成 system prompt section，每轮都被动注入，模型会在每轮推理中"被迫看到"洞察——这就不是"参考"而是"干扰"了

### render 输出格式

工具的 `output.render` 把结构化 JSON 渲染成人类可读的 Markdown：

```
## 认知洞察（建议，非约束）
- [warn] causal@1的原因置信度下降：置信度连续 2 轮下降（最新 62%），趋势需关注。
- [info] 深层归因动力学苗头：因果链的原因与时间链的过去内容重叠（3个共同关键词）...

## 推荐话题
- [convergence] 分析已经很完整了，要不要开始执行？（因果链所有角色已填充，置信度 85%。）
- [extension] 关于这个分歧，要不要展开讨论一下？（AI 推论"人力不足"与用户路径"需求混乱"分歧尚未收敛。）
```

标题明确标注"建议，非约束"——让模型在阅读时就知道这不是指令。

```yaml
chains:

```

```
chains.enabled = true, chains.insight.enabled = false
  → 链图正常记录，但不启动洞察引擎（v0.2.0 的行为）

chains.enabled = true, chains.insight.enabled = true
  → 链图正常记录 + 洞察引擎每轮分析 + get_insights tool 可用
```

### 版本兼容性

洞察引擎是纯增量功能：
- 不修改 ChainGraph 的任何行为（只读）
- 不修改快照解析协议
- 不修改 prompt.ts 的图鉴内容
- `insight.enabled = false` 时，系统行为与 v0.2.0 完全一致

| 维度 | 融合进阶.md | 洞察引擎.md（本文档） |

| 产出物 | prompt.ts 催化酶提示词 | insight.ts 五大分析器 |

`融合进阶.md` 解决的是"如何让 CoT 自发产生链间嫁接"——它通过催化酶提示词让模型形成嗅觉直觉。

`洞察引擎.md` 解决的是"如何让系统理解链间嫁接正在发生"——它通过程序化分析检测化学反应苗头、置信度趋势等全局信号。

两者互补：模型靠嗅觉嫁接，系统靠洞察理解。模型不一定要看系统的洞察——但如果它调取了 `get_insights`，它会获得一个"自己可能没意识到的全局视角"。

### 与 `chain-design-final.md` 的分工

`chain-design-final.md` 定义了链图的骨架——五链类型、角色、演化语义、快照协议。它是"语法"。

`洞察引擎.md` 在这个语法之上构建了"语义理解"——不只是"causal@1.cause 的内容是什么"，而是"causal@1.cause 与 temporal@1.past 的内容重叠意味着什么"。

### 与 prompt.ts 的关系

`prompt.ts` 是给模型内化的图鉴——模型通过它学会"如何思考"。

`insight.ts` 是给系统运行的分析器——系统通过它学会"如何观察模型的思考"。

两者完全不耦合：`prompt.ts` 不知道 `insight.ts` 的存在，`insight.ts` 也不修改 `prompt.ts` 的内容。模型可以选择永远不调 `get_insights`，它的推理质量不会因此下降——洞察引擎是"加分项"，不是"必选项"。

## 七、设计哲学：为什么是"建议"而不是"指令"

### 核心矛盾

任何认知增强系统都面临一个根本矛盾：

- **太弱**：只记录不分析 → 系统有数据没理解（v0.2.0 的 ChainGraph + ChainGuide）
- **太强**：分析后强制注入 → 系统干预了 CoT 的推理自由度（被设计文档明确否定的 SELECT/REFACTOR/INJECT 路径）
- **恰到好处**：分析后以建议形式暴露 → 系统有理解但不干预（洞察引擎的选择）

### "建议"的三重保障

洞察引擎通过三重机制确保"建议"不会变成"指令"：

**保障一：产出形态**

洞察产出是 `InsightItem`——有 type、severity、title、detail，但没有任何"action"字段。它描述"正在发生什么"，不规定"应该做什么"。推荐话题虽然是问句形式（"要不要展开聊聊？"），但那是对用户的引导，不是对模型的指令。

**保障二：递送方式**

洞察通过 tool 暴露，不通过 system prompt 注入。模型必须**主动调用** `get_insights` 才能看到洞察内容。这意味着：
- 模型在深度推理中时，完全不会被洞察打扰
- 模型主动调取洞察这个行为本身，是它判断"我需要全局视角"的结果——这是 CoT 的一部分
- 模型看到洞察后可以完全忽略——因为标题明确写了"建议，非约束"

**保障三：生命周期隔离**

洞察引擎的存储跟会话绑定，不跨会话。这意味着：
- 洞察不会"累积"成一种持续的干预力量
- 每个新会话都是干净的开始
- 洞察的影响力被限制在单个会话内

### 与设计方案终局共识的一致性

设计方案的终局共识是：

> CoT 放权——系统只做两件事：
> 1. 在 System Prompt 中注入五链图鉴（prompt.ts）
> 2. 在模型回复末尾解析 JSON 快照（hook.ts）
> prestep 零干预。

洞察引擎严格遵循这个共识：
- 它不修改 system prompt（图鉴内容不变）
- 它不修改 prestep（零干预原则不变）
- 它只是在快照解析之后，"顺便"做了一些分析——这些分析的产出不回流到模型的推理过程中，除非模型主动来问

如果把系统比作一个房间：图鉴是墙上挂的认知地图（模型抬头就能看到），快照是桌上的笔记本（系统在记录），洞察引擎是角落里的观察员（在旁边做笔记，你问他才说，不问不说）。

## 八、实现架构与文件关系

### 数据流全景

```
assistant/message 事件
        ↓
  hook.ts 监听器
        ↓
  index.ingest()
    ├── parseSnapshot()           解析 JSON 快照行
    ├── stripSnapshotLine()       剥离 JSON 行（用户不可见）
    ├── mergeSnapshotIntoGraph()  融合入 ChainGraph（单链演化记录）
    ├── g.prune()                 裁剪
    └── buildGuide()              元数据投射（GPS/轨道图/缺口）
        ↓
  insightEngine.analyze()         ← 超然层入口
    ├── updateConfidenceHistory()  追加本轮置信度到历史
    ├── 5 个分析器并行执行（纯函数，互不依赖）
    │   ├── analyzeCrossReaction()    链间化学反应
    │   ├── analyzeMigration()        链迁移预测
    │   ├── analyzeConfidenceTrend()  置信度趋势
    │   ├── analyzeGapAggregation()   缺口聚合
    │   └── analyzeDivergence()       分歧收敛
    ├── appendInsights()           去重 + FIFO 入库（上限 20）
    └── generateTopics()           话题生成 → appendTopics()（上限 10）
        ↓
  get_insights tool（模型按需调取）
        ↓
  session/disposed → dispose()     一并销毁（链图 + 洞察 + 置信度历史）
```

### 文件职责

| 文件 | 职责 |
|------|------|
| `src/chains/insight.ts` | 洞察引擎实现：5 个分析器 + 话题生成器 + 会话内存储 |
| `src/chains/types.ts` | 类型定义：InsightItem / RecommendationTopic / InsightStore / InsightEngine |
| `src/chains/hook.ts` | 接入点：ingest 后调用 analyze()，session/disposed 联动销毁 |
| `src/index.ts` | 生命周期管理：创建 InsightEngine，注册 get_insights tool |
| `src/config.ts` | 配置：chains.insight.enabled |

### 分析器的纯函数设计

5 个分析器全是纯函数——输入是 ChainGraph + ChainGuide（+ InsightStore），输出是 InsightItem[]。它们：

- 不修改 ChainGraph（只读）
- 不修改 InsightStore（`analyzeConfidenceTrend` 只读 `confidenceHistory`，写入由 `updateConfidenceHistory` 单独负责）
- 互不依赖（可以任意顺序执行，结果不变）

这种设计保证了分析器可以被独立测试，且不会产生意外的副作用。

## 九、未来推演方向

### 短期（可能在本版本之后立即跟进）

1. **化学反应检测升级**：从关键词交集升级为 embedding 相似度，提高检测精度
2. **话题渲染 UI**：实现 `/insights` 命令或会话结束便条的 UI 渲染
3. **分析器测试覆盖**：为 5 个分析器编写独立单元测试（红→绿）

### 中期

4. **语义角色映射**：缺口聚合不再只看"终结角色"，而是跨链映射语义等价角色（如因果链的"方案"与操作链的"结果"在语义上都是"结论性产出"）
5. **链迁移模式学习**：积累多会话数据后，分析常见的链迁移路径（如"因果→操作"是最频繁的迁移），优化迁移预测的准确率
6. **情绪-洞察联动**：结合 prompt.ts 的"情绪即底色"，在情绪高水位时降低洞察的 severity（避免在用户焦虑时推送 critical 级别的预警）

### 长期

7. **跨会话洞察**：将洞察的置信度趋势等信号写入 agent-memory，实现跨会话的认知模式追踪（这会突破当前"随会话生灭"的约束，需要重新评估生命周期设计）
8. **自适应图鉴**：根据洞察结果动态调整 prompt.ts 的图鉴内容（如根据链迁移频率调整嗅觉催化提示的权重）——这会突破超然层定位，需要重新评估"建议 vs 指令"的边界

**设计原则不变：洞察引擎是观察者，不是参与者。它只看，不想；只建议，不指挥。**
