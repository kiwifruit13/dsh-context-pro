# API、接口与胶水代码开发全链路公约

> 本文件是项目的「架构与编码总纲」，定义了从**对外暴露（API）**、**内部契约（接口文件）** 到 **跨层适配（胶水代码）** 的完整规范。Claude Code 启动时自动加载，作为团队协作的共同基线。
>
> **最后更新**：2026-07-28
> **适用范围**：所有涉及前后端分离、微服务调用及跨语言集成的项目

---

## 0. 核心哲学（先思后行）

**不假设、不隐藏困惑、显式权衡。**
在编写任何 API、接口或胶水代码之前，必须遵守以下准则：

- **显式陈述假设**：若不确定调用方会如何传参或下游会如何响应，立即提问，不擅自编造逻辑。
- **契约优先**：先定义接口契约（API Spec / IDL），后编写实现代码和胶水逻辑。
- **胶水轻薄**：胶水代码只做连接和转换，绝不包含核心业务规则。
- **可观测**：所有对外 API 和跨层胶水必须有日志、监控和分布式追踪。
- **简单第一**：修改尽可能简单，影响范围最小；根治问题，禁止临时打补丁。

## 1. API 设计规范（对外门面层）

API 是系统对外暴露的**物理入口**（如 HTTP/REST 或 gRPC 服务），解决“提供什么能力”和“如何访问”的问题。

### 1.1 URL 端点设计（RESTful 风格）

| 规范 | 说明 |
|------|------|
| **名词复数** | 使用名词复数表示资源集合，`GET /users`，`POST /orders` |
| **禁用动词** | 操作交给 HTTP 方法，不在 URL 中出现 `/getUser` 或 `/createOrder` |
| **层级表达从属** | 使用 `/` 表达资源归属，如 `/users/{id}/orders` |
| **命名风格** | URL 路径统一使用 **kebab-case**（小写+短横线），如 `/user-profiles` |
| **查询参数** | 用于过滤、排序、分页，如 `?status=active&sort=created_at:desc&page=2` |

### 1.2 HTTP 方法与幂等性铁律

| 方法 | 语义 | 幂等性 | 请求体 | 成功状态码 |
| :--- | :--- | :--- | :--- | :--- |
| **GET** | 获取资源 | ✅ 是 | 禁止携带 | 200 / 404 |
| **POST** | 创建资源 | ❌ 否（重复创建多条） | 携带数据 | 201 / 400 |
| **PUT** | 全量更新（替换） | ✅ 是 | 携带完整数据 | 200 / 204 |
| **PATCH** | 部分更新 | ❌ 否（建议保证重试安全） | 携带差异数据 | 200 / 204 |
| **DELETE** | 删除资源 | ✅ 是 | 禁止携带 | 204 / 404 |

### 1.3 请求与响应体结构

- **字段命名**：团队统一选择 **`camelCase`（驼峰）** 或 **`snake_case`（蛇形）**，严禁混用。
- **统一包装层**（非简单查询场景推荐使用）：
  ```json
  {
    "code": 0,
    "message": "success",
    "timestamp": 1723456789000,
    "data": { ... }
  }
  ```
- **时间格式**：强制使用 **ISO 8601** 字符串（`2026-07-28T10:30:00Z`）或 **毫秒级时间戳**，二选一，严禁使用 `2026/07/28` 歧义格式。
- **货币/金额**：统一使用 **最小单位整数**（如分）或 `string` 类型，**严禁**使用 `float/double`。

### 1.4 HTTP 状态码 vs 业务错误码（双轨制）

- **HTTP Status**：代表传输层/网关/鉴权状态（200/401/403/500），不承载业务错误。
- **业务 `code`**：代表业务层状态，在响应体中返回。

| 场景 | HTTP 状态码 | Body 中 code |
| :--- | :--- | :--- |
| 正常返回 | 200 | `0` 或 `"SUCCESS"` |
| Token 失效 | 401 | `10001` |
| 无权限 | 403 | `10003` |
| 参数校验失败 | 400 | `20001` |
| 业务冲突（库存不足） | 200（或 409） | `30002` |

### 1.5 版本控制策略

- **路径版本**：在 URL 第一级携带版本号，如 `/v1/users` → `/v2/users`。
- **兼容性规则**：
  - ✅ **允许（小版本）**：新增可选字段、扩展枚举值（客户端忽略未知值）。
  - ❌ **禁止（破坏性变更）**：删除字段、将可选改为必填、修改字段语义。
  - 破坏性变更必须升大版本，且新旧版本需并存维护至少 3 个月过渡期。

### 1.6 分页与排序标准化

- **传统偏移分页**（后台表格）：`page`（从 1 起）、`size`；返回 `total`、`pages`。
- **游标分页**（App 无限下拉）：`cursor`、`limit`；返回 `next_cursor`。
- **排序**：统一参数 `sort=字段:顺序`，多个用逗号分隔，如 `?sort=created_at:desc,id:asc`。

## 2. 接口文件契约规范（代码图纸层）

接口文件是编程语言或 IDL 层面的**纯静态契约**，解决“能调什么”和“参数长什么样”的问题。

### 2.1 文件组织与命名

| 规范 | 说明 |
|------|------|
| **存放路径** | 统一放在 `/api/<模块>/<版本>/` 目录下 |
| **文件命名** | PascalCase（大驼峰），如 `UserService.proto`、`PaymentAPI.go` |
| **版本标识** | 文件名或路径中必须显式包含版本信息 |
| **同文件聚合** | 同一服务的请求、响应、接口定义放在同一个文件中 |

### 2.2 命名约定

| 类型 | 规范 | 示例 |
|------|------|------|
| **接口名** | PascalCase，建议加 `I` 前缀（视语言而定） | `IUserService` |
| **方法名** | PascalCase，动词+名词 | `GetUserByID`、`CreateOrder` |
| **请求/响应** | PascalCase + `Req`/`Res` 或 `Request`/`Response` 后缀 | `GetUserReq`、`CreateOrderResponse` |
| **枚举常量** | UPPER_SNAKE_CASE | `ORDER_STATUS_PENDING` |

### 2.3 契约设计原则

- **职责单一**：遵循接口隔离原则（ISP），不设计“大而全”的上帝接口。
- **类型明确**：所有字段类型必须明确定义（如 `int64`、`string`、`Timestamp`）。
- **幂等性声明**：接口定义中需注明方法是否幂等，指导调用方重试策略。
- **演进兼容**：已发布的字段不可删除或改变类型。新增字段需标记为 `optional`。

### 2.4 特定技术栈补充

| 技术栈 | 补充规范 |
|--------|----------|
| **Protobuf/gRPC** | `service` 和 `rpc` 方法使用 PascalCase；文件命名为 `<service>.proto` |
| **OpenAPI/Swagger** | 契约文件与代码实现同步更新，禁止手写维护过时的 YAML |
| **Java Interface** | 接口方法必须抛出明确声明的异常，或使用 `CompletableFuture` 封装异步结果 |

## 3. 胶水代码实现规范（连接适配层）

胶水代码是连接不同模块、语言或协议的**动态运行层**，解决“如何让 A 和 B 协同工作”的问题。

### 3.1 职责边界（红线）

- **只做连接**：胶水代码的职责仅限于**类型转换、参数适配、协议转换、调用转发**。
- **禁止业务逻辑**：胶水代码中**不得**包含价格计算、状态机流转、权限判定等核心业务规则。
- **薄层原则**：胶水代码应集中在系统边界（如 Controller 层、外部 SDK 封装层），避免散落各处。
- **可替换性**：胶水代码的任一方法应可随时删除或替换，而不影响核心骨骼逻辑。

### 3.2 健壮性要求

- **前置校验**：对入参进行非空、类型、范围校验，作为第一道防线。
- **禁止全局状态**：严禁在胶水层使用全局可变变量或单例持有请求上下文。
- **异常翻译**：所有下游异常必须被捕获并转换为调用方期望的错误格式（如统一的业务 `code`）。
- **超时与熔断**：跨系统调用必须设置超时（Timeout），合理配置重试（注意幂等性）和熔断策略。

### 3.3 可观测性强制要求

- **统一日志格式**：胶水代码日志必须包含：`traceId`、`caller`、`callee`、`req`、`res`、`cost_ms`。
- **链路追踪传递**：必须在 HTTP Header 或 RPC Context 中透传分布式追踪 ID，确保全链路可追溯。
- **错误归档**：胶水层转换失败或调用超时时，必须输出结构化的错误日志，包含失败阶段、下游返回原文、修复建议。

### 3.4 特定技术栈实践

| 场景 | 规范 |
|------|------|
| **C++ ↔ Python（pybind11）** | 绑定代码写在 `PYBIND11_MODULE` 宏中，使 Python 侧调用风格自然、符合 Python 习惯 |
| **C++ → C 封装层** | 编写薄薄的 C Wrapper 作为胶水，仅暴露 `extern "C"` 接口，不暴露 C++ 特性 |
| **跨语言 RPC** | IDL 编译器自动生成的 Stub 代码属于胶水层，人工只补充额外的适配转换逻辑 |
| **脚本串连（Shell/Python）** | 脚本只做流程编排和数据搬运，不做任何业务计算 |

## 4. 三者边界与协作关系（理解误区澄清）

| 维度 | **API（门面）** | **接口文件（图纸）** | **胶水代码（翻译）** |
| :--- | :--- | :--- | :--- |
| **本质** | 可运行的物理入口 | 静态的代码/文本契约 | 动态执行的转换逻辑 |
| **关注点** | 网络地址、协议、鉴权、业务功能 | 方法名、参数类型、返回值类型 | 数据适配、参数转换、调用转发 |
| **包含逻辑** | ✅ 包含核心业务实现 | ❌ 纯声明，无实现 | ✅ 包含适配/转换逻辑（非业务） |
| **生命周期** | **运行期**（7x24h 监听端口） | **编译/开发期**（IDE 和编译器使用） | **运行期**（在调用链路上执行） |
| **变动物影响** | 变更影响外部调用方，需版本管理 | 变更需重新编译部署实现类 | 变更一般只影响连通性，不改核心 |

**协作流程示例**（Java 调用 Python AI 服务）：
1.  **接口文件**：定义 `.proto` 契约（图纸）。
2.  **胶水代码**：Java 中编写 HTTP Client 封装，做 JSON 序列化/反序列化（翻译）。
3.  **API**：Python 服务启动在 `http://ai.service:8080` 处理请求（门面）。

## 5. 通用评审检查清单

在提交涉及 API、接口或胶水代码的 PR 前，逐项确认：

### ✅ API 设计检查
- [ ] URL 是否使用名词复数，且路径为 kebab-case？
- [ ] HTTP 动词与幂等性要求是否匹配？
- [ ] 响应体是否使用了统一的包装结构（如有）？
- [ ] 时间、金额字段是否使用了指定格式类型？
- [ ] 业务错误码是否在全局错误码表中已定义？
- [ ] 破坏性变更是否伴随版本升级和过渡期计划？

### ✅ 接口文件检查
- [ ] 接口命名是否清晰、职责单一？
- [ ] 所有字段类型是否明确且不可变？
- [ ] 是否有破坏性变更（删除/重命名字段）？
- [ ] 新增字段是否标记为可选或提供默认值？

### ✅ 胶水代码检查
- [ ] 是否包含不应有的业务逻辑或算法？
- [ ] 输入参数是否做了非空/类型前置校验？
- [ ] 是否完整记录了调用日志并透传了 traceId？
- [ ] 下游调用是否配置了超时和合理的重试策略？
- [ ] 异常是否被捕获并转换为统一错误格式？

# 工程标准与 API 规范

> 本文档是工程层面的"宪法"，定义所有可量化的技术指标与接口契约。
> 任何代码、文档、Agent 产出均须满足本文档约束。

---

## 1. API 设计规范

### 1.1 命名与风格

| 对象 | 规则 | 示例 |
|------|------|------|
| URL 路径 | `kebab-case` | `/api/v1/user-orders` |
| 接口 / 方法名 | `PascalCase` | `GetUserOrder` |
| 请求 / 响应字段 | `camelCase`（对外）或 `snake_case`（内部） | `orderId` / `order_id` |
| 枚举值 | `UPPER_SNAKE_CASE` | `ORDER_STATUS_PAID` |

### 1.2 版本与兼容

- URL 中携带主版本号：`/api/v1/...`。
- 新增字段向后兼容；废弃字段保留至少一个大版本。

### 1.3 错误响应

- 统一结构：`{ "code": int, "message": string, "traceId": string }`。
- `code` 全局唯一，维护在 `docs/error-codes.md`。

## 2. 数据契约

- 所有对外接口必须维护 `openapi.yaml`（≥ 3.0）。
- `tests/test_api_contract.py` 断言 `__all__` 可访问性及枚举完整性。
- 接口变更必须同步更新契约文件，否则 CI 拒绝合并。

---

## 3. 胶水代码规范

### 3.1 适用范围

- C++ ↔ Python 绑定
- C → C++ 封装层
- 跨语言 RPC 桥接
- 消息队列序列化 / 反序列化适配

### 3.2 实现要求

- 只做类型转换与调用转发，禁止包含业务逻辑。
- 保持可替换性：替换底层实现时胶水层接口不变。

### 3.3 日志标准（强制）

每条胶水层日志必须包含以下字段：

| 字段 | 说明 |
|------|------|
| `traceId` | 全链路追踪 ID |
| `caller` | 调用方标识 |
| `callee` | 被调方标识 |
| `timestamp` | ISO 8601 格式 |
| `duration_ms` | 耗时 |
| `status` | `success` / `fail` / `timeout` |

## 4. 质量门禁标准

> 以下为所有量化指标的权威定义。AGENTS.md 中引用本节。

### 4.1 覆盖率

| 指标 | 最低要求 |
|------|----------|
| 行覆盖率（Line Coverage） | ≥ 80% |
| 分支覆盖率（Branch Coverage） | ≥ 75% |
| 核心模块（标记 `@critical`） | 行 ≥ 90%，分支 ≥ 85% |

### 4.2 复杂度

| 指标 | 阈值 |
|------|------|
| 圈复杂度（Cyclomatic Complexity） | ≤ 10 / 函数 |
| 认知复杂度（Cognitive Complexity） | ≤ 15 / 函数 |
| 函数长度 | ≤ 50 行（不含空行与注释） |

### 4.3 重复率

- 代码重复率 ≤ **5%**（以 SonarQube / jscpd 检测为准）。
- 连续重复块 ≥ 6 行即计为重复。

### 4.4 静态分析规则集

| 语言 | 工具 | 规则等级 |
|------|------|----------|
| Python | `ruff` + `mypy --strict` | 0 error, 0 warning |
| TypeScript / JS | `eslint`（`@typescript-eslint/recommended`） | 0 error |
| C / C++ | `clang-tidy` + `cppcheck` | 0 error |
| Go | `golangci-lint` | 0 error |

### 4.5 编译与类型检查

- 所有语言必须在 CI 中执行完整编译，`-Werror`（C/C++）或 `--strict`（TS）开启。
- 类型检查零错误。

### 4.6 测试通过要求

- 单元测试：100% 通过，不允许 skip / xfail（除非关联 Issue）。
- E2E：关键路径用例（标记 `@smoke`）100% 通过。
